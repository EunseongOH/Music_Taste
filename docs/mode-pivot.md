> **원칙 (2026-09-21 운영자 확정)**
> 믹스 매치는 **사용자 페이지에서 격리만** 한다. 지우는 것이 아니다.
> - 코드: 한 줄도 지우지 않는다(`genres/page.tsx` 포함). 플래그로 가리기만 한다.
> - DB: 열·데이터·초안 전부 그대로. 마이그레이션 없음.
> - 검사·문서: 한 커밋에 묶어 되돌릴 수 있게만 바꾼다.
> - 되살리기: `MIX_MATCH = true` + 토스 라우트 2줄 + 검사 커밋 revert (§10, 5분).
>
> 이 원칙에 어긋나는 제안(파일 삭제, 열 삭제, 데이터 정리)은 이 문서 범위 밖이다.

## 2. 왜 지금인가 — 근거

### 2.1 쿼터는 이미 두 번 터졌다 (실측)

`spotify_429_log` 전체:

| 날짜 | 엔드포인트 | 이유 | 차단 시간 | 그날 호출 수 |
|---|---|---|---|---|
| 2026-09-16 | `/v1/artists/{id}/albums` | QUOTA_EXCEEDED | 85,618초 (≈24h) | (기록 전) |
| 2026-09-17 | `/v1/artists/{id}/albums` | QUOTA_EXCEEDED | 40,283초 (≈11h) | **81** |

**하루 81콜에서 터졌다.** 그리고 게이트(`spotify_endpoint_gate`)는 **세는 것과 터진 뒤 막는 것**만 한다 — 사전 상한이 없어서, 한도가 어디든 우리는 매번 벽에 부딪히고 나서야 멈춘다.

> ⚠️ **이 계획의 가장 중요한 사실**: 터진 엔드포인트 `/v1/artists/{id}/albums` 는 **믹스 매치가 아니라 한 아티스트 전곡 모드**가 쓰는 것이다. 믹스 매치를 내리는 것만으로는 쿼터 문제가 풀리지 않는다. 그래서 이 문서는 **2부(§7 비용 대책)를 반드시 함께** 실행하는 것을 전제로 한다.

오늘(9/21) 집계: `/v1/albums/{id}/tracks` 197 · `/v1/search` 90 · `/v1/artists/{id}/albums` 59.

#### 무엇이 태웠나 — 확인됨 (2026-09-21)

| 9/17 | 값 |
|---|---|
| `/v1/artists/{id}/albums` 호출 | **81** (여기서 차단) |
| 그날 완성된 취향표 | **0건** |
| 그날 앨범 캐시에 새로 담긴 아티스트 | **3명** |

**원인: 전곡 모드에서 아티스트를 여러 명 검색해 트랙리스트까지 불러본 것**(소트는 진행하지 않음). 운영자 확인. 버그가 아니다.

그런데 이게 버그보다 나쁜 소식이다. **아티스트를 둘러보는 것만으로 하루치 쿼터가 날아간다**는 뜻이기 때문이다.

- 전곡 모드에서 아티스트를 고르면 `/tracks` 가 **그 자리에서 전 앨범 목록 + 전 앨범의 곡 목록**을 백그라운드로 끝까지 받는다(`tracks/page.tsx:584-684`, 800ms 간격).
- 평균 아티스트 한 명 = 앨범 목록 3콜 + 곡 목록 26콜 ≈ **29콜**.
- **어떤 아티스트로 할지 고민하며 3~4명 열어보는 건 이용자의 자연스러운 행동이다.** 그러면 한 사람이 90~120콜을 쓰고, 그날 서비스 전체가 잠긴다.

**단, 이용자가 아티스트를 이렇게 여러 명 열어보는 일은 흔하지 않다**(운영자 판단). 그래서 대책은 "둘러보기를 막는 것"이 아니라 **둘러볼 때 눌리는 아티스트가 이미 DB 에 있게 만드는 것**이다 — 지금은 피드에 뜨는 아티스트의 2.4% 만 곡 목록이 있다. §7.1 이 그 대책이고, 프리페치 구조 자체는 건드리지 않는다(§7.3).

### 2.2 믹스 매치가 태우는 호출은 캐시가 먹지 못한다

| 호출 | 누가 | 캐시 |
|---|---|---|
| `/v1/artists/{id}/related-artists` | **믹스 매치 전용** (단일 모드는 `explore/page.tsx:613` 에서 먼저 빠져나간다) | 메모리 10분뿐, **DB 캐시 없음** |
| 위 호출 실패 시 폴백 장르 검색 | 믹스 매치 | **랜덤 오프셋 20~100** + 캐시 조회가 이름 ilike 라 **히트율 ≈ 0** |
| 장르 무한스크롤 `/v1/search` | 믹스 매치 기본 동선 (스크롤 1회당 최대 3콜) | 부분적 |
| `/v1/artists/{id}/albums`, `/v1/albums/{id}/tracks` | **한 아티스트 전곡 모드** | DB 캐시 21일 → **같은 아티스트 두 번째 사용자부터 Spotify 0콜** |

추정(코드 배수 기준, 실측 아님) — 아티스트 8명 한 판: 믹스 매치 약 89콜 중 **24~42콜이 재사용 불가**. 단일 모드 한 판 약 85콜은 **전부 캐시에 쌓여 다음 사람에게 0콜**이 된다.

즉 두 모드의 콜 수는 비슷하지만 **성격이 정반대다.** 단일 모드의 비용은 *적립*이고 믹스 매치의 비용은 *소모*다. DB를 모으는 지금 단계에서 소모성 호출을 먼저 끄는 게 맞다.

### 2.3 Supabase 대역폭도 믹스 매치 쪽이 무겁다

- Spotify 콜 1회 = Supabase 요청 최소 1건(게이트 RPC), 캐시 미스면 3건. 콜이 줄면 그대로 줄어든다.
- `tournament_drafts.selected_tracks` 자동저장(1.5초 디바운스)이 **선택 곡 배열 전체**를 매번 올린다. 아티스트 8명분(수백 곡) → 1명분으로 줄면 판당 수백 KB → 수십 KB.
- (모드와 무관한 별건) `explore-taste`·`archive` 가 `tournament_results` 를 **`select("*")` + limit 없이** 읽는다. 공개 결과가 쌓일수록 진입마다 선형으로 커진다. §7.4 에 둔다.

### 2.4 사용 데이터가 이미 그렇게 움직였다

| | 전체 결과 | 최근 30일 | 평균 곡 수 |
|---|---|---|---|
| 한 아티스트 | 15 | **8** | 39 |
| 믹스 매치 | 27 | **1** | 16 |

진행 중 드래프트: 한 아티스트 9건(최근 4건) · 믹스 매치 6건 **전부 8월 9일 이전**. → **진입점을 닫아도 진행 중인 판을 끊지 않는다.**

### 2.5 목표에 맞다

초기 목표가 "소트라는 놀이를 알리는 것 + 같은 아티스트를 좋아하는 사람끼리 주고받게 하는 것"이라면, 같은 곡 세트를 공유하는 고리(`/together`)는 **한 아티스트 모드에서만 성립한다**. 믹스 매치 결과는 남에게 건네도 같이 할 수가 없다.

## 3. 복원 가능성 — 어떻게 보장하나

**방식: 기능 플래그 한 개 + 커밋 경계 + 태그.** 파일을 지우지 않는다.

```ts
// src/config/modes.ts
/**
 * 믹스 매치 월드컵(여러 아티스트) 모드.
 * 2026-09-21 비용·집중 이유로 내렸다. 되살리는 법: docs/mode-pivot.md §10.
 */
export const MIX_MATCH = false;
```

- 화면·링크·메타데이터는 이 상수로 가린다. 코드는 그대로 남는다 → `MIX_MATCH = true` 한 줄로 웹은 즉시 복원된다.
- 토스 빌드만 예외다. 라우트 표(`toss/app/src/App.tsx`)에서 빼야 **번들에서도 빠진다**(관리자 화면을 빼는 것과 같은 방식). 주석으로 한 줄 복원법을 남긴다.
- 검사 스크립트의 믹스 매치 케이스는 **한 커밋으로 묶어** 지운다 → `git revert <그 커밋>` 으로 되살린다.
- 작업 끝에 태그 `mix-match-off` 를 찍는다. 그 직전 커밋이 "믹스 매치가 살아 있던 마지막 상태"다.

**하지 않는 것**: 파일 삭제, DB 열 삭제, 기존 데이터 정리. (`tournament_drafts.is_single_artist` 는 upsert 유니크 키라 지우면 전부 깨진다.)

## 6. 같이 소트하기 진입점 (드디어 정한다)

믹스 매치가 비운 자리에 넣는다. 홈 카드 수는 4장 그대로.

| 순서 | 카드 | 목적지 |
|---|---|---|
| 1 | 최애 곡 소트하기 | `/explore?mode=single` |
| 2 | **같이 소트하기** (새로) | `/together` |
| 3 | 내 취향 스페이스 | `/explore-taste` |
| 4 | 우리의 취향 아카이브 | `/archive` |

카드 문구(초안): 뱃지 "둘 이상" · 제목 "같이 소트하기" · 설명 "같은 곡을 각자 소트하고, 취향이 얼마나 닮았는지 확인해요." · 버튼 "시작하기"

추가 진입점 두 곳 (P4):

## 7. 비용 대책 — 남기는 모드 쪽 (이게 진짜 절반이다)

핵심은 하나다. **이용자가 열어보는 아티스트가 이미 DB에 있으면 비용은 0이다.** 지금 문제는 둘러보기 자체가 아니라, 피드에 뜨는 아티스트의 대부분이 DB에 없다는 것이다.

| 지금 | 수 |
|---|---|
| 피드·검색에 뜰 수 있는 아티스트(메타데이터 캐시) | **2,779명** |
| 그중 곡 목록까지 확보된 아티스트 | **67명 (2.4%)** |
| 그중 전곡 확보(coverage ≥ 0.9) | **28명** |

피드에서 아무 아티스트나 누르면 **97.6% 확률로 콜드 페치**(약 29콜)다. 반대로 말하면, **피드를 확보된 아티스트로 채우는 것만으로 둘러보기 비용이 거의 사라진다.**

### 7.0 개발·검사가 운영 쿼터를 태우지 않게 한다 (가장 먼저, 가장 쌈)

9/17 차단은 운영자가 아티스트 여러 명을 열어보다 난 것이다. 로컬 개발 서버도, Playwright 검사도 **운영과 똑같은 Spotify 앱·똑같은 쿼터**를 쓴다. 이용자가 없는 날에도 문이 닫힌다.

**구현 완료 (2026-09-21).** `src/utils/spotify.ts` 의 `spotifyFetch` 맨 앞에서 끊는다.

- `NODE_ENV !== "production"` 이면 **기본으로 켜짐**. 운영만 꺼짐. `SPOTIFY_CACHE_ONLY=0` 으로 끄고 `=1` 로 켠다(운영에서 켜면 쿼터를 다 쓴 날의 비상 브레이크가 된다).
- 켜져 있으면 Spotify 도, **게이트 RPC 도** 부르지 않는다(호출 수가 늘면 안 된다). 503 을 돌려주고 호출부는 기존 실패 경로대로 캐시/빈 결과로 간다.
- `lastSpotifyError` 는 건드리지 않는다 — 화면에 연결 오류 배너를 띄울 일이 아니다. 대신 서버 로그에 한 번만 알린다.
- 확인: 개발 서버를 다시 띄우고 `/explore?mode=single` 에서 검색 → 화면은 DB 캐시(아티스트 2,779명)로 정상 렌더, `spotify_endpoint_quota` 수치는 **하나도 늘지 않음**.
- 남는 구멍 두 개: `npm run db:warmup` 은 `spotifyFetch` 를 지나지 않는다(일부러 담는 도구라 그대로 둔다). **Vercel 프리뷰는 `NODE_ENV=production` 이라 켜지지 않는다** — 프리뷰에서 쿼터가 새면 그 환경변수에 `1` 을 넣는다.

### 7.1 피드를 "확보된 아티스트"로 채운다 (핵심 대책)

`/explore?mode=single` 의 기본 목록을 **`together_artist_catalog` 뷰**(`coverage` = 곡까지 받아 둔 앨범 ÷ Spotify 가 말한 앨범 수) 기준으로 정렬한다. 같이 소트하기 만들기 화면이 이미 쓰는 방식·API 를 그대로 쓴다.

- **목록을 자르지 않고 순서만 바꾼다** — 전곡 확보(28명) → 부분 확보(45명) → 나머지. 다양성을 잃지 않으면서 눌리는 쪽이 확보된 아티스트가 된다.
- **확보 여부를 화면에 적지 않는다.** 이용자는 당연히 전곡이 있다고 생각하고 들어온다. "전곡 있어요/일부만 있어요"를 붙이면 **없는 쪽을 우리가 먼저 알리는 꼴**이라 약점만 드러낸다. 확보율은 순서로만 쓴다(2026-09-21 결정 · 같이 소트하기 화면에서도 같은 이유로 걷어냄 — 커밋 참조).
- 정말 곡이 모자라 소트가 안 되는 아티스트는 **고르는 순간에만** 알린다("이 아티스트는 아직 담긴 곡이 적어요"). 드문 경우를 상시 라벨로 만들지 않는다.
- 이름으로 검색해 들어오는 길은 **그대로 연다.** 내 최애 아티스트가 아직 없으면 그때 담는 게 맞다 — 그 29콜은 낭비가 아니라 적립이다(그 사람은 실제로 소트한다).

효과가 세 겹이다: 둘러보기 0콜(비용) · 고른 순간 곡이 바로 뜸(속도) · 곡이 다 있는 아티스트로 자연스럽게 유도(품질).

**다른 세션의 검색 폴백과는 축이 다르다(2026-09-21, main `f82f831` 대기 중).** 그쪽은 Spotify 검색이 막혔을 때 `searchDbArtists()` 로 **이름을 찾는** 문제를 푼다(`artist_serve_snapshot` 2,200팀 + `name_ko` 로 "아이유"→IU). 이 계획은 **누른 아티스트에 곡이 있는가**를 푼다. 검색으로 찾아지는 2,200팀 중 곡 목록까지 있는 건 67팀이라, 폴백만으로는 클릭 비용이 그대로다 — 두 가지가 다 필요하다.

- 병합 뒤 확인할 것: 피드(`getInitialArtists`)와 검색 폴백이 **서로 다른 출처**를 본다. 피드는 coverage 순으로 바꾸고, 검색은 폭을 유지한다(발견을 막지 않는다).
- 검사에 영향: 아티스트 검색은 예산이 0이어도 **빈손이 아니다**(DB 가 답한다). 곡 검색은 예산 90% 초과 시 빈 배열이다.

**한계와 성장 경로**: 지금 확보 풀이 67명이라 피드 상단이 반복적으로 보일 수 있다. 이건 canonical 작업이 채우는 만큼 자동으로 넓어진다 — **성공 지표를 `coverage ≥ 0.9` 아티스트 수로 잡으면 서비스 화면과 정확히 같은 값**이 된다(부록 C).

### 7.2 엔드포인트 일일 예산 — **이미 있다** (main → develop 병합 완료)

계획할 때는 새로 만들 생각이었는데, 다른 세션이 이미 넣어 두었다(main `5c16afe`·`3e1a960`, develop 에 병합 `2416760`).

| 엔드포인트 | 하루 예산 | 어디서 |
|---|---|---|
| `/v1/artists/{id}/albums` | **50** | `getArtistAlbums` 가 Spotify 를 부르기 직전 |
| `/v1/albums/{id}/tracks` | **600** (`SPOTIFY_TRACK_BUDGET`) | `getAlbumTracks` 가 부르기 직전 |

`endpointBudgetLeft(endpoint, budget)` 가 `spotify_endpoint_quota.calls_today` 를 읽어 예산이 남았는지 본다. 예산을 다 쓰면 **조용히 빈 결과**를 돌려준다(캐시·DB 경로는 그 위에서 이미 반환되므로 영향 없음).

→ **`daily_limit` 열을 새로 만들지 않는다.** 계획에 있던 마이그레이션은 취소한다. 대신 남은 일은 둘뿐이다.

1. 예산 숫자 재검토: albums 50 은 9/17 차단(81콜)보다 보수적이라 지금은 맞다. §7.1 이 들어가 둘러보기가 캐시로 흡수되면 그때 다시 본다.
2. ~~`/v1/search` 예산~~ — **다른 세션이 가져갔다**(main `f82f831`, 푸시 대기). 한 통(`SPOTIFY_SEARCH_BUDGET`, 기본 200)을 쓰되 멈추는 선이 셋이다: 장르 피드 60% · 곡 검색 90% · 아티스트 검색 100%. 장르 무한스크롤이 예산을 태우고 사람이 친 검색이 죽는 순서를 막는다.

⚠️ 캐시 전용 모드(§7.0)와 예산 가드는 **둘 다 "조용히 빈 결과"** 를 돌려준다. 검사 스크립트에서 빈 트랙 목록을 실패로 단정하지 않는다(다른 세션 지적).

### 7.3 전곡 프리페치 미루기 — **하지 않는다(관찰 후 재검토)**

한때 "아티스트를 열면 앨범 목록만 받고, 곡 목록은 확정 뒤에"로 바꾸려 했다. **보류한다.**

- 7.1 이 들어가면 피드에서 열리는 아티스트는 대부분 이미 확보돼 있어 **어차피 0콜**이다.
- 이름으로 검색해 들어온 아티스트는 실제로 소트할 확률이 높다 — 그 29콜은 적립이다.
- 지금 UX(고르면 전곡이 바로 준비됨)를 건드리는 변경이라 비용 대비 위험이 크다.

**다시 볼 조건** — 아래 지표가 계속 3을 크게 웃돌면 둘러보기 낭비가 실재하는 것이므로 그때 바꾼다.

```sql
-- 하루 앨범 목록 콜 ÷ 그날 새로 담긴 아티스트 수. 3 근처면 낭비 없음.
select q.day, q.calls_today,
       (select count(distinct artist_id) from spotify_cache_artist_albums
         where cached_at::date = q.day) as new_artists
from spotify_endpoint_quota q
where q.endpoint = '/v1/artists/{id}/albums';
```

### 7.4 Supabase 읽기: 페이지네이션 (확정) · 선호 아티스트 (후순위)

**지금 할 것 — 페이지네이션.** `explore-taste/page.tsx:212-232` 와 `archive/page.tsx:304-307` 이 `tournament_results` 를 `select("*")` + limit 없이 읽는다. 행마다 `ranking` jsonb(곡 전체: 제목·아티스트·커버 URL)가 붙어 있어 결과가 쌓이는 만큼 진입 비용이 선형으로 커진다. 목록에 필요한 열만 고르고 20건씩 끊어 받는다.

**나중에 — 선호 아티스트.** 이용자가 늘면 "무엇을 20건 보여줄까"가 문제가 된다. 그때는 등록해 둔 선호 아티스트로 **그 아티스트를 소트한 다른 리스너의 취향표를 먼저** 보여준다. 같은 자리에서 정렬 기준만 바뀌므로, 지금 페이지네이션을 넣어 두면 그때 얹기만 하면 된다. **이 전환의 범위 밖·후순위.**

`spotify.ts` 의 캐시 조회 4곳은 서버↔DB 라 사용자 체감과 무관하다. 손대지 않는다.

### 12.1 왜 301 이 아니라 302 인가

301 은 "영구히 이사했다", 302 는 "지금은 저쪽을 보세요"다. 우리는 **언제든 되살릴 전제**로 접으므로 302 가 사실에 맞다. 301 을 쓰면 검색엔진이 `/genres` 를 색인에서 지우고 점수를 옮기는데, 복원해도 되돌아오는 데 오래 걸린다. 어느 쪽이든 **404(막다른 길)보다 낫다** — 검색·북마크·메신저 링크로 들어온 사람이 빈 화면을 보지 않는다.

### 12.2 상한 숫자의 근거

전곡이 찬 아티스트 20명 기준 **평균 앨범 26장(중앙값 19)**. 새 아티스트 한 명을 처음 담는 비용은 앨범 목록 `ceil(26/10)` ≈ 3콜 + 앨범별 곡 목록 ≈ 26콜 = **약 29콜**.

- §7.1 **적용 전**: 피드 아티스트의 97.6% 가 DB 에 없어, 아무거나 3명 눌러보면 87콜 → 현재 예산(albums 50)이면 첫 사람이 그날을 다 쓴다.
- §7.1 **적용 후**: 피드에서 여는 아티스트는 대부분 0콜. 이름으로 검색해 새로 담는 아티스트만 29콜 → 현재 예산(albums 50 · tracks 600) 안에서 **하루 새 아티스트 16명** 남짓.
