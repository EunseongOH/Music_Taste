# "전곡 확보"의 정의 — 합의가 필요한 초안

2026-09-22 · 읽기 전용 조사 결과 (Spotify 호출 0회, DB 변경 없음)

사용자 지적에서 출발한다. "까치산의 경우 일부 앨범 곡이 몇 개 빠져있어. 지금 전곡을 확보했다고
말한 게 실은 틀릴 수 있다는 의미야."

맞다. 그런데 까치산 한 명의 문제가 아니었고, 데이터가 모자란 것도 주된 원인이 아니었다.
**"전곡 확보"라는 말이 코드 여덟 군데에서 각각 다른 것을 뜻하고 있었다.**

---

## 0. 지금 상태

"곡까지 낼 수 있다"고 표시되는 아티스트 **62명 중, 표시가 실제와 맞는 사람은 30명**이다.

같은 아티스트(까치산)를 두고 시스템이 내놓는 숫자들:

| 출처 | 값 | 세는 것 |
|---|---|---|
| `together_artist_catalog.track_count` | 33 | 캐시된 트랙 배열 길이의 단순 합 |
| `artist_serve_snapshot.tracks_servable` | 22 | 세 출처 트랙 행의 합 (중복 계수) |
| `artist_serve_snapshot.albums_servable` | 9 | sp+mb+dz 앨범 수의 합 (중복 계수) |
| `artist_serve_snapshot.sp_albums` | 7 | Spotify 앨범에 연결된 MB 발매판 |
| `together_artist_catalog.albums_total` | 11 | Spotify 가 말한 앨범 수 |

다섯 숫자가 전부 다르고, 전부 "그 아티스트의 분량"을 뜻한다고 읽힌다.

## 1. 판정 기준이 있는 여덟 곳

| # | 위치 | 무엇을 세는가 | 문제 |
|---|---|---|---|
| 1 | `together_artist_catalog.coverage` | 곡이 **하나라도** 캐시된 앨범 / max(나열 앨범, Spotify 가 말한 앨범 수) | 12곡짜리에 1곡만 있어도 "확보" |
| 2 | `together_artist_catalog.track_count` | 캐시된 트랙 배열 길이의 합 | 중복 제거 없음 |
| 3 | `/api/together/catalog?servable=1` | `track_count >= 8` | coverage 를 안 본다 |
| 4 | `PICK_COVERAGE = 1` (이번주 추천) | `coverage = 1.0` | #1 의 약점을 그대로 물려받음 |
| 5 | `artist_serve_snapshot.albums_servable` | sp + mb + dz 앨범 수의 합 | 같은 앨범을 출처마다 중복 계수 |
| 6 | `artist_serve_snapshot.tracks_servable` | 세 출처 트랙 행의 합 | 중복 계수 + songKey 미적용 |
| 7 | `dbCatalog` 서빙 판정 | `tracks_filled_at` 있는 것 → 앨범 병합 → songKey 중복 제거 | **유일하게 화면과 일치** |
| 8 | `/tracks` 머리말 `countDistinctTracks` | 이미 받아 둔 앨범 안의 서로 다른 곡 | 아직 안 받은 앨범은 못 셈 |

### 구조적 문제 하나

**같이 소트하기는 `spotify_cache_*` 만 읽는다. `dbCatalog`(MusicBrainz·Discogs·Deezer)를 한 번도 안 본다.**

그래서 두 화면이 서로 다른 곡 세계를 본다.

```
같이 소트하기가 "곡이 있다"고 보는 아티스트      62명
자체 DB 로 곡을 낼 수 있는 아티스트           2,106명
그중 이미 위 62명에 들어 있는 사람                50명
```

62명 중 50명은 이미 자체 DB 에도 있다. 즉 같이 소트하기는 **2,106명을 쓸 수 있는데 62명만 쓰고
있고**, 그 62명조차 더 정확한 출처(자체 DB)를 두고 Spotify 캐시를 본다.

## 2. 정의 후보 — 숫자를 붙였다

대상은 지금 "곡까지 낼 수 있다"고 표시되는 62명이다.

### 안 A — 엄격

> Spotify 가 아는 모든 앨범의 모든 곡을, songKey 중복 제거 후 화면에 낼 수 있다.

**62명 중 20명 (32%)**

가장 정직하지만 통과 기준이 너무 높다. 슈퍼디럭스판·지역판·컴필레이션까지 전부 요구한다.
Spotify 가 말한 앨범 수(`total`)에는 우리가 목록조차 못 받은 앨범이 포함돼서, 아이유가
coverage 0.182 로 나오는 것도 이 때문이다(8장은 온전한데 Spotify 는 44장이라고 한다).

### 안 B — 정규 앨범 기준 (추천)

> 정규 앨범·컴필레이션의 곡은 빠짐없이, 싱글은 80% 이상 낼 수 있다.
> 화면 필터로 사라지는 곡이 없다.

**62명 중 30명 (48%)**

"전곡"이라는 말을 이용자가 이해하는 대로 쓴다. 이용자는 싱글 리패키지 열 장을 다 원하지
않는다. 정규 앨범에 구멍이 없으면 "전곡"이라 불러도 속이는 게 아니다.

### 안 C — 화면 진실

> 나열된 앨범에 전부 트랙리스트가 있고, 화면 필터로 사라지는 곡이 없다.

**62명 중 32명 (52%)**

가장 느슨하다. "우리가 아는 범위 안에서는 빠짐이 없다"는 뜻이라, Spotify 가 아는데 우리가
목록조차 못 받은 앨범은 묻지 않는다. 구현이 제일 쉽지만 사용자 지적을 온전히 풀지는 못한다.

**세 안 모두 지금보다 정직하다.** 지금은 62명 전부를 "곡 있음"으로 취급한다.

## 3. 수렴 계획

### 남길 것 하나

`artist_coverage`(가칭) **뷰 하나**가 정의를 계산하고, 나머지는 전부 그것을 읽기만 한다.

계산 근거는 **7번(`dbCatalog` 서빙 판정)** 이어야 한다. 여덟 중 유일하게 화면이 실제로 내는
것과 같은 규칙(앨범 병합 + songKey)을 쓰기 때문이다. 나머지는 전부 그 근사치다.

| 지금 | 이후 |
|---|---|
| 1 `coverage` | 새 뷰의 `coverage` 로 교체 (분모를 "우리가 아는 앨범"으로) |
| 2 `track_count` | 새 뷰의 `distinct_tracks` (songKey 적용) 로 교체 |
| 3 `servable=1` | 새 뷰 한 컬럼(`is_full`) 읽기 |
| 4 `PICK_COVERAGE` | 같은 컬럼 읽기 |
| 5 `albums_servable` | **남기되 이름을 바꾼다** — `album_rows_by_source`. 수집 진척용이지 화면용이 아님을 이름으로 못박는다 |
| 6 `tracks_servable` | 같은 처리 — `track_rows_by_source` |
| 7 `dbCatalog` | **정본.** 새 뷰가 이 규칙을 따라간다 |
| 8 `/tracks` 머리말 | 그대로 (이미 7과 같은 규칙) |

### 두 화면이 같은 곡 세계를 보게 하는 법

같이 소트하기의 `/api/together/catalog` 가 `spotify_cache_*` 대신 `dbCatalog` 를 읽게 한다.

- 이득이 크다. 추천 가능 아티스트가 62명 → 최대 2,106명이 된다.
- `titleKey` 를 버리고 `songKey` 를 쓰게 된다. 일본어·중국어 제목이 사라지는 (다) 버그가
  **원인째 없어진다** — `songKey` 는 유니코드 문자 클래스를 쓴다.
- 캐시 만료에 흔들리지 않는다. 지금은 21일 캐시가 비면 추천 목록도 같이 빈다.

다만 이건 66 담당 파일(`api/together/catalog/route.ts`)이고 (다)·(가) 수정과 겹친다.
**순서를 정해야 한다** — 66 이 `titleKey` 를 고친 뒤 이 교체를 하면 그 수정이 버려진다.
`titleKey` 수정을 건너뛰고 바로 `dbCatalog` 전환으로 가는 편이 나아 보이는데, 전환이
하루 이상 걸린다면 임시 수정이 먼저인 게 맞다. 판단이 필요하다.

## 5. 작업 범위와 위험

| 항목 | 범위 |
|---|---|
| 마이그레이션 | 뷰 1개 추가(`artist_coverage`). 추가 전용. 기존 뷰·테이블 안 건드림 |
| 뷰 이름 변경(5·6) | `artist_serve_coverage` 를 고쳐야 한다. **읽는 곳이 스크립트 여러 개** — 이름을 바꾸면 같이 고쳐야 한다. 안 바꾸고 주석만 다는 선택지도 있다 |
| 서비스 코드 | `api/together/catalog/route.ts`(66) · `explore/page.tsx`(66) |
| 스크립트 | `export-coverage-xlsx.ts` · `check-missing.ts` 가 기존 지표를 쓴다. 정의가 바뀌면 보고서 숫자도 바뀐다 |

**위험 셋**

1. **숫자가 내려간다.** "62명 확보" → 안 B 로 30명. 후퇴로 보이지만 지금 숫자가 틀린 것이다.
   같이 소트하기를 `dbCatalog` 로 옮기면 오히려 크게 올라간다(최대 2,106명).
2. **정의를 코드로 못 박으면 되돌리기 어렵다.** 뷰 하나에 모아 두면 되돌릴 자리도 하나다.
   그래서 뷰를 먼저 만들고 화면을 나중에 옮긴다.
3. **66 작업과 겹친다.** 위 §3 의 순서 판단.

## 5-1. 실시간이 아니다 (2026-09-22 추가)

`artist_coverage` 를 화면에서 바로 읽으면 느리다. 실측:

| 무엇 | 비용 |
|---|---|
| `is_full` 만 | 버퍼 443,791 · 2,809ms |
| 위를 상관 서브쿼리 없이 재작성 | 버퍼 7,704 · 734ms |
| **`distinct_tracks` 까지** | **7,315ms · 23.5MB 디스크 정렬** |

`distinct_tracks` 는 `count(DISTINCT unnest(h_base))` 라 트랙 해시 68만 행을 풀어 정렬한다.
인덱스로 해결되지 않는다 — 요청마다 할 일이 아니라 배치로 할 일이다.
(같이 소트하기 진입이 운영에서 6~9초였던 원인이 이것이다.)

그래서 **`artist_coverage_cached`**(materialized view)를 두고 화면·API 는 그것을 읽는다.
`REFRESH MATERIALIZED VIEW CONCURRENTLY` 를 **매시 27분**에 돌린다(pg_cron). 읽기는 안 막힌다.

**따라서 "전곡 확보"는 실시간이 아니다. 최대 1시간 낡는다.**
수집이 30분 주기라 이용자가 알아챌 차이는 아니지만, 다음을 염두에 둬야 한다.

- 수집 직후 확인할 때는 `artist_coverage`(뷰)를 직접 읽는다. 느리지만 최신이다.
- 화면에서 "방금 채운 아티스트가 왜 아직 안 보이나"는 **버그가 아니라 갱신 대기**다.
- 정의를 바꾸려면 `artist_coverage` 뷰만 고친다. 캐시는 복사본이라 따로 고칠 것이 없다.

## 관련 후속 (같이 우선순위를 정할 것)

지금 작업은 아니고, 사용자가 한 번에 순서를 정하기 좋게 모아 둔다.

1. **`getArtistDiscography` 되살리기** — 전곡을 Spotify **0회**로 부르는 경로.
   지금 `/tracks` 는 `loadRemainingPagesInBackground` 로 앨범마다 Spotify 를 부른다.
   canonical 에 있었으나 develop 에 없어 통합에서 제외했다(2026-09-22).
2. **`searchTracksByQuery` 의 DB 우선** — 곡 검색이 통째로 Spotify 의존이다.
   검색 예산 90% 선을 넘기면 "결과 없음"이 된다. 아티스트 검색은 이미 DB 폴백이 있다.
3. **`getAlbumTracks` 의 50곡 상한** — 60곡 이상 앨범 5장이 잘린다(총 85곡).
   전부 슈퍼디럭스판이고 앨범 합치기가 원본 뒤로 숨겨서 실피해는 거의 없다. 우선순위 낮음.
4. **일치율 서버 계산** — 별건으로 이미 제기돼 있다.

1·2 는 이 문서의 주제와 같은 성격이다 — **DB 로 답할 수 있는데 Spotify 를 부른다.**
