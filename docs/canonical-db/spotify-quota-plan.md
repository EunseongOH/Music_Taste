# Spotify 제한 없이 "전곡"을 즉시 제공하기 위한 계획

작성일: 2026-09-17 · 브랜치: `feat/canonical-db` · 상태: 제안 (사용자 결정 필요 항목 포함)

---

## 0. 목표와 우선순위

이 계획의 모든 판단은 아래 순서를 따른다. 위 항목과 충돌하면 아래 항목을 양보한다.

1. **Spotify API 제한에 걸리지 않는다.** 한 번 걸리면 해당 기능이 최대 24시간 멈춘다.
2. **전곡을 보장한다.** 이용자가 고른 아티스트의 Spotify 앨범 전체 트랙이 빠짐없이 보여야 한다. 일부만 보이면 "전곡 소트"가 성립하지 않는다.
3. **빠르게 보여준다.** 가능한 한 DB와 캐시에서 즉시 응답한다.
4. **DB 확보 속도.** 느려도 된다. 1~3을 해치지 않는 범위에서만 늘린다.

"전곡"의 기준은 **Spotify 앨범 목록**이다. 이용자가 소트하는 곡이 Spotify에 있는 곡이기 때문이다. MusicBrainz 등 DB는 그 목록의 트랙리스트를 Spotify 대신 채우는 역할이고, 목록 자체를 대신하지 않는다.

## 1. 현재 상태 (2026-09-17 실측)

### 1.1 수요 (운영 데이터)

| 항목 | 값 | 비고 |
|---|---|---|
| 저장된 소트 결과 | 49건 (5/26 이후), 최근 7일 16건 | 저장하지 않은 세션은 빠진 수치 |
| 앨범 목록이 열린 아티스트 | 57명 (캐시 유효 35명) | 운영 21일 캐시 기준 |
| 트랙리스트가 열린 앨범 | 1,002개 (캐시 유효 579개) | 아티스트당 평균 약 18개 |
| 앨범당 평균 곡 수 | 6곡 | 싱글 비중이 높다 |
| 소트 후보 곡 수 | 평균 22, 최대 203 | |

### 1.2 DB 커버리지

| 항목 | 값 |
|---|---|
| 열린 아티스트 중 정식 매핑(url_rel/manual) | **52 / 57 (91%)** |
| 열린 앨범 중 DB 트랙리스트 보유 | **393 / 1,002 (39%)** ← 핵심 병목 |
| 트랙리스트까지 확보한 아티스트 | 약 1,800명, 곡 약 20만 |
| DB 용량 | 110MB / 무료 플랜 500MB |

아티스트는 거의 다 있다. **문제는 앨범 단위 연결이다.** MusicBrainz에 트랙리스트가 있어도 그 발매판에 Spotify 앨범 링크가 없으면 연결되지 않는다. 예: 박효신은 MB 발매그룹 32개가 있지만 Spotify 앨범과 연결된 건 5개뿐이다.

### 1.3 Spotify 쿼터에 대해 알고 있는 것

| 사실 | 근거 |
|---|---|
| 쿼터는 **엔드포인트별 일일 한도**로 동작한다 | 2026-09-16 `/v1/artists/{id}/albums`만 `429 QUOTA_EXCEEDED`, 검색·아티스트 조회는 정상 |
| 한도를 넘으면 Retry-After 약 24시간 | 실측 85,618초 |
| 계정 단위라 운영·로컬·워커가 한 통을 쓴다 | Spotify 2026-07 정책 |
| **앨범 목록 엔드포인트 한도는 수백 회 수준으로 추정** | 로컬 약 120회 + 소규모 운영 트래픽에서 소진. 정확한 수치는 **미상** |

마지막 줄이 계획 전체에서 가장 큰 불확실성이다 (가설 H0).

### 1.4 이용자 동작별 Spotify 호출 경로 (브랜치 코드 기준)

| 이용자 동작 | 엔드포인트 | 캐시 | DB 대체 |
|---|---|---|---|
| 아티스트 검색 | `/v1/search` | 메모리 1시간 | canonical 우선, 없을 때만 호출 |
| 탐색 첫 화면·장르 | `/v1/search` | DB 21일 + 야간 워밍 | canonical 우선 |
| 아티스트 앨범 목록 열기 | `/v1/artists/{id}/albums` | DB 7일 (전 이용자 공유) | **대체하지 않음 (전곡 기준)** |
| 앨범 트랙리스트 | `/v1/albums/{id}/tracks` | DB 21일 (전 이용자 공유) | MB와 연결된 앨범은 호출 0 |
| 싱글 모드 전곡 선택 | 위 둘의 조합 | 위와 같음 | 빠진 앨범 5개 이하면 한 번에, 초과면 페이지별 |
| 곡 검색 | `/v1/search` (track) | 메모리 | canonical 우선 |

## 2. 핵심 원리: 호출 수를 이용자 수가 아니라 카탈로그 크기에 묶는다

공유 캐시가 있으면 같은 아티스트·앨범을 몇 명이 보든 호출은 캐시 수명당 한 번이다. 하루 호출 수의 상한은 대략 다음과 같다.

```
앨범 목록 호출/일  ≈ (일주일간 열린 서로 다른 아티스트 수) ÷ 7
앨범 트랙 호출/일  ≈ (열린 아티스트 수 × 18 × (1 − DB 커버율)) ÷ 21
```

| 주간 활성 아티스트 | 앨범 목록/일 | 앨범 트랙/일 (커버 39%) | 앨범 트랙/일 (커버 80%) | 앨범 트랙/일 (커버 95%) |
|---|---|---|---|---|
| 200 | 29 | 105 | 34 | 9 |
| 500 | 71 | 261 | 86 | 21 |
| 2,000 | 286 | 1,046 | 343 | 86 |

첫 열람이 서로 다른 날에 고르게 퍼진다는 단순 가정이다. 여기서 두 가지 결론이 나온다.

- **동시접속자 수 자체는 문제가 아니다.** 같은 키를 동시에 여는 요청을 하나로 합치기만 하면 된다 (H5).
- **문제는 활성 아티스트가 늘 때 두 엔드포인트의 일일 한도다.** 앨범 목록 한도가 수백 회라면 주간 활성 아티스트 2,000명에서 이미 위험하다. 그래서 커버율 올리기(H1, H2)와 앨범 목록 호출 줄이기(H4)가 둘 다 필요하다.

## 3. 가설별 계획

각 가설은 **내용 → 기대 효과 → 필요한 것 → 검증 → 위험** 순서로 적는다.

### H0. 엔드포인트별 일일 한도를 실측한다 — 모든 것의 전제

**내용.** 엔드포인트별 호출 수를 세고, 429가 났을 때 그날의 누적 호출 수를 기록해 한도를 역산한다. 계측 테이블(`spotify_endpoint_quota`)과 엔드포인트 단위 차단기는 이미 브랜치에 있다 (커밋 ac8b0bc).

**기대 효과.** 아래 모든 예산 수치(워밍 예산, TTL)를 추정이 아닌 실측으로 정한다.

**필요한 것.**
- **운영 코드에 계측과 차단기만 먼저 반영.** 지금은 브랜치에만 있어서 운영 트래픽이 세어지지 않는다. main 반영이므로 **사용자 허가가 필요하다.** 변경 범위는 `spotifyFetch` 진입부와 429 처리부뿐이고, 계측이 실패하면 그냥 통과시킨다.
- 429 발생 시 그 시점 `calls_today`를 남기는 기록 테이블 1개 (additive).

**검증.** 한 번이라도 429가 나면 그 시점 `calls_today`가 한도의 근사치다. 429가 안 나면 그날 최대 호출 수가 "안전하다고 확인된 하한"이 된다.

**위험.** 거의 없다.

---

### H1. 앨범 연결률을 제목·연도·곡 수 대조로 올린다 — 효과 가장 큼

**내용.** 워커가 이미 캐시된 Spotify 앨범 목록(제목, 발매일, 곡 수)과 MusicBrainz 발매판을 대조한다. 세 조건이 **모두** 같을 때만 연결한다.

1. 정규화한 제목이 완전히 같다 (대소문자, 공백, 특수문자, "(Deluxe)" 류 접미 처리 규칙을 고정)
2. 발매연도가 같다
3. 곡 수가 같다

URL 링크로 연결된 것과 구분할 수 있게 연결 근거를 따로 기록한다.

**기대 효과.** 추가 Spotify 호출 0회. 열린 앨범 DB 커버율 39% → 목표 80%. 2장 표 기준 앨범 트랙 호출이 약 1/3로 준다.

**필요한 것.**
- 스키마: 별도 테이블 `mb_album_title_match (spotify_album_id, release_mbid, matched_at)` (additive, 기존 CHECK 제약은 건드리지 않음)
- 워커: 대조 단계 1개. 대상은 앨범 목록 캐시가 있는 정식 매핑 아티스트
- **사전 측정 (코드 반영 전):** 운영 캐시에 이미 있는 57명의 앨범 목록으로 대조만 돌려 연결률과 오연결 표본을 뽑는다. Spotify 호출 0회
- **사용자 도움:** 대조 결과 50건 O/X 검수

**검증.** 검수 표본에서 오연결 0건이면 적용한다. 적용 후 "열린 앨범 중 DB 트랙리스트 보유 비율"을 주 단위로 본다.

**위험.** 잘못 연결되면 곡 목록이 틀려 전곡 보장이 깨진다. 세 조건 동시 일치로 막고, 애매하면 연결하지 않는 쪽(= Spotify에서 받는 쪽)으로 기운다.

---

### H2. Discogs 월간 덤프로 트랙리스트 빈칸을 채운다

**내용.** Discogs 데이터 덤프(CC0, 이미지 제외)에서 우리 아티스트의 발매판 트랙리스트만 스트리밍으로 추출해 저장하고, H1과 같은 규칙으로 Spotify 앨범과 연결한다. Discogs API는 저장 기간 제한 조항이 있어 쓰지 않는다.

**기대 효과.** MusicBrainz에 없는 옛 음반(산울림, 이승철, 델리스파이스 류)의 트랙리스트 확보. 추가 Spotify 호출 0회.

**필요한 것.**
- 덤프 다운로드(압축 약 10GB)와 스트리밍 파서, 저장 테이블 `discogs_release`, `discogs_track` (additive)
- 실행 환경: 로컬 PC 또는 GitHub Actions. 무료 플랜 용량 안에 들어가도록 우리 아티스트만 저장
- **사전 측정:** H1 적용 후에도 연결 안 된 앨범 50개를 뽑아 Discogs에 있는지 확인. 한국 디지털 싱글은 약할 것으로 예상

**검증.** 사전 측정에서 50개 중 20% 미만이면 보류한다.

**위험.** 디지털 싱글 커버리지가 낮아 노력 대비 효과가 작을 수 있다. 그래서 H1 다음 순서다.

---

### H3. 이용자가 열기 전에 미리 캐시한다 — 예산제 워밍

**내용.** 수요가 예상되는 아티스트의 앨범 목록과 트랙리스트를 새벽에 미리 받아 둔다. **엔드포인트별 일일 예산**을 넘지 않고, 429가 한 번이라도 나면 즉시 멈춘다.

워밍 대상 우선순위:
1. 최근 7일 안에 열렸고 캐시가 곧 만료되는 아티스트 (다시 열릴 가능성이 높음)
2. 탐색 첫 화면·장르 페이지에 노출되는 아티스트
3. 사용자가 제공한 차트·인기 명단
4. 신곡 신호가 온 아티스트 (H4)

**기대 효과.** 낮 시간 이용자 요청의 캐시 적중률이 오르고, 호출이 피크 시간에서 새벽으로 옮겨간다.

**필요한 것.**
- 테이블 `warm_targets (spotify_id, priority, reason, last_warmed_at)` (additive)
- 스케줄러 1개. 예산은 H0 실측 한도의 30% 이내, KST 03~07시만
- **사용자 결정 필요:** 현재 원칙은 "워커·로컬에서 Spotify 호출 금지"다. 워밍은 이 원칙의 **예외**이므로 허용 여부와 예산 비율을 정해야 한다
- 기존 야간 워밍(`spotify-warmup.yml`, 검색 엔드포인트)이 canonical에 있는 아티스트를 건너뛰게 수정 (main 반영 사항)

**검증.** 워밍 후 낮 시간 캐시 적중률. 워밍이 쓴 호출 수가 예산 이하인지.

**위험.** 수요 예측이 틀리면 한도만 소비한다. H0 실측 전에는 시작하지 않는다.

---

### H4. 캐시 수명을 아티스트 상태에 맞춘다 — 앨범 목록 호출 절감

**내용.** 모든 아티스트에 같은 7일을 쓰지 않는다.

| 아티스트 상태 | 앨범 목록 TTL | 근거 |
|---|---|---|
| 최근 60일 안에 발매 있음 | 3일 | 후속곡·리패키지 가능성 |
| 최근 1년 안에 발매 있음 | 7일 | 현재값 |
| 1년 넘게 발매 없음 | 21일 | 약관상 임시 캐시로 쓰는 상한과 같음 |

추가로 **신곡 신호**가 오면 TTL과 무관하게 한 번 갱신한다. 신호는 Spotify를 부르지 않고 얻는다. 워커가 MusicBrainz를 새로고침할 때 새 발매그룹이 생겼는지를 본다.

만료 시각에 무작위 편차(±10%)를 줘서 같은 날 대량 만료로 호출이 몰리지 않게 한다.

**기대 효과.** 열리는 아티스트 중 오래 활동이 없는 아티스트가 많을수록 앨범 목록 호출이 크게 준다. 실측 전 추정은 절반 이하.

**필요한 것.**
- 앨범 목록 캐시의 최신 발매일로 TTL 계산 (코드만, 스키마 변경 없음)
- 워커의 MB 새로고침에서 "새 발매그룹 생김"을 캐시 무효화로 연결

**검증.** 적용 전후 `/v1/artists/{id}/albums`의 `calls_today`.

**위험.** 오래 쉬던 아티스트의 깜짝 발매는 최대 21일 늦게 보인다. MB 신호로 일부 보완되지만 MB 등록이 늦으면 못 잡는다. **신곡 반영 지연 허용치는 사용자 결정 사항이다.**

---

### H5. 동시접속 시에도 같은 키는 한 번만 부른다 — 요청 경로 보호

**내용.**
1. **인스턴스 간 중복 제거.** 지금의 중복 합치기는 서버 인스턴스 안에서만 동작한다. 캐시가 없는 같은 아티스트를 여러 인스턴스가 동시에 열면 인스턴스 수만큼 호출한다. DB에 키별 짧은 잠금(10초)을 두고, 잠금을 못 얻은 요청은 잠깐 기다렸다가 캐시를 읽는다.
2. **만료 후 즉시 응답, 뒤에서 갱신 (soft/hard TTL).** soft TTL이 지나면 기존 캐시로 즉시 응답하고 갱신은 백그라운드에서 한 번만 한다. hard TTL(21일)이 지나면 더는 쓰지 않는다.
3. **차단 중 우아한 저하.** 엔드포인트가 차단되면 hard TTL 안의 캐시로 응답한다. 캐시도 없으면 DB에 있는 앨범부터 보여주고 나머지는 대기 표시를 한다. 이때 **전곡이 아니라는 사실을 화면에 명시한다.**

**기대 효과.** 동시접속자가 늘어도 호출 수가 늘지 않는다. 캐시 만료 순간의 응답 지연이 사라진다.

**필요한 것.**
- 테이블 `spotify_fetch_lease (key, locked_until)` 또는 기존 잠금 함수 재사용 (additive)
- soft TTL 판단은 캐시 테이블의 기존 `cached_at` 사용 (스키마 변경 없음)
- UX: "전곡 N/M 불러옴" 진행 표시 (**사용자 결정:** 문구·위치)

**검증.** 같은 아티스트를 동시에 50회 여는 부하 테스트에서 Spotify 호출 1회. 부하 테스트에서 실제 Spotify 호출은 모의(mock)로 대체한다.

**위험.** 잠금 대기가 길어지면 응답이 느려진다. 대기 상한을 두고, 넘으면 페이지 단위 로딩으로 넘어간다.

---

### H6. 아티스트 목록·검색의 Spotify 의존 제거

**내용.**
- 검색어 → 아티스트 ID 결과를 DB에 7일 캐시한다. 지금은 메모리에만 있어 인스턴스마다 새로 호출한다.
- 야간 워밍이 canonical에 이미 있는 아티스트를 건너뛰게 한다.
- canonical 검색에 MB 별칭·한글명·사용자 제공 이름을 모두 쓴다 (일부 적용됨).

**기대 효과.** `/v1/search`는 "DB에 없는 새 아티스트 검색"에만 쓰인다.

**필요한 것.** 테이블 `artist_search_cache (normalized_query, ids, expires_at)` (additive). 야간 워밍 수정은 main 반영 사항.

**검증.** `/v1/search`의 `calls_today`.

---

### H7. 사람이 채우는 경로를 상시화한다

**내용.** 지금 대화로 주고받는 "이름 : Spotify ID" 작업을 상시 경로로 만든다.
- 제출 테이블 `artist_link_submissions (spotify_id, name, submitted_at, status)`와 관리자 입력 화면
- 워커가 제출분을 MusicBrainz만으로 판정해 매핑한다. 규칙은 지금 쓰는 그대로다: MB에 같은 링크가 있으면 연결, 격리 매핑이 발매 있는 한국·일본 항목이면 승격, 아니면 이름 검색 후보 중 발매가 있는 항목
- 판정이 애매한 건은 관리자 확인 대기

**기대 효과.** 격리·미확인 아티스트 해소가 대화 없이 진행된다.

**필요한 것.** 위 테이블과 화면. **사용자 도움:** 링크 제공 (남은 명단 135명).

## 6. 성공 지표와 확인 쿼리

| 지표 | 현재 | 목표 |
|---|---|---|
| 429 발생 | 2026-09-16 1회 | 0 |
| 엔드포인트별 일일 호출 / 실측 한도 | 미측정 | 50% 미만 (워밍 포함) |
| 열린 앨범 중 DB 트랙리스트 보유 | 39% | 80% 이상 |
| 싱글 모드에서 전곡이 한 번에 로드되는 비율 | 미측정 | 90% 이상 |
| 열린 아티스트 중 정식 매핑 | 91% | 97% 이상 |

```sql
-- 엔드포인트별 오늘 호출 수와 차단 상태
SELECT endpoint, calls_today, blocked_until
FROM spotify_endpoint_quota ORDER BY calls_today DESC;

-- 실제로 열린 앨범의 DB 커버율
SELECT count(*) AS used,
       count(*) FILTER (WHERE EXISTS (
         SELECT 1 FROM mb_album_release r
         WHERE r.spotify_album_id = c.album_id AND r.tracks_filled_at IS NOT NULL)) AS with_db_tracks
FROM (SELECT DISTINCT album_id FROM spotify_cache_album_tracks) c;

-- 트랙리스트가 아직 없는 아티스트
SELECT * FROM canonical_coverage WHERE status <> 'tracklist' ORDER BY release_groups DESC;
```

## 7. 하지 않을 것

- 웹 크롤링, 타사 ID 조회 도구 자동화, 웹 플레이어 내부 API 사용 — Spotify와 해당 사이트 약관 위반, 앱 키 정지 위험
- 멜론·지니·벅스·바이브·플로 수집 — 저작권법(데이터베이스제작자 권리)과 부정경쟁방지법(데이터 부정사용) 위반
- Client ID 여러 개로 쿼터 분산 — 쿼터가 계정 단위라 효과가 없고 약관 위반 소지
- Spotify 메타데이터 영구 저장 — 임시 캐시(21일)까지만
- DB에 일부만 있는 앨범 목록으로 Spotify 앨범 목록을 대체 — 전곡 보장이 깨진다
- Apple Music, Deezer, YouTube, TIDAL, Last.fm, Genius를 데이터 소스로 사용 — 광고 수익화 금지, 비상업 한정, 저장 기간 제한 등

## 8. 미확인 사항과 위험

| 항목 | 영향 | 대응 |
|---|---|---|
| 엔드포인트별 일일 한도 수치 | 모든 예산의 기준 | H0 |
| Spotify의 한도·정책 재변경 | 예산 재조정 | 엔드포인트 차단기가 자동으로 막음, 계측으로 조기 감지 |
| 21일 캐시가 약관상 "임시"로 인정되는지 | 캐시 전략 전체 | hard TTL을 상수 하나로 두어 필요 시 바로 단축 |
| 제목 대조 오연결 | 전곡 보장 훼손 | 세 조건 동시 일치 + 검수 |
| MusicBrainz 신곡 등록 지연 | 신곡 신호 누락 | TTL 상한으로 결국 갱신됨 |
| 무료 플랜 500MB | Discogs 보강 시 증가 | 우리 아티스트만 저장, 주간 용량 확인 |
