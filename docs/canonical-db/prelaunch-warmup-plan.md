## ★ 3일 압축판 (2026-09-17 결정: 홍보 약 3일 뒤 시작)

아래 원래 계획(1~8장)은 한 달 이상을 전제로 한다. 3일 안에는 다음이 달라진다.

**전제 변경.** 운영(sortify.kr)은 main 코드로 돈다. main에는 DB(MusicBrainz) 우선 조회가 없으므로, 3일 안에 이용자 체감을 바꾸는 방법은 **운영이 읽는 21일 Spotify 캐시를 운영과 같은 모양으로 미리 채우는 것**뿐이다. canonical 브랜치 병합은 홍보 전에 하지 않는다 (안정성 검증 시간이 없음).

**대상 (prelaunch_targets, 2026-09-17 생성).** 1군(S) 487명: 큐레이션 첫 화면, 실제 이용, 차트, 아이돌·팬덤 목록, 사용자 링크. 2군(A) 162명: 페스티벌·J-Pop, 인디.

**작업량 (호출 없이 계산).**

| 작업 | 1군 | 2군 | 3일 안 가능 여부 |
|---|---|---|---|
| 앨범 목록 캐시 (50개씩 받아 10개 단위로 저장) | 약 560회 | 약 195회 | 가능 (하루 150~250회 × 3일) |
| 앨범 트랙 캐시 | 약 16,900회 | 약 5,800회 | **불가능.** 우선순위 일부만 |

**3일 일정.**

| 날 | 할 일 | Spotify |
|---|---|---|
| D-3 (오늘) | 엔드포인트 게이트 hotfix main 병합 (사용자). 대상 명단 확정, 수집 스크립트 준비 (완료) | 0 |
| D-2 새벽 | 1군 앨범 목록 150회로 시작 → 429 없으면 같은 날 +100 | 150~250 (앨범 목록) |
| D-1 새벽 | 1군 나머지 + 2군 앨범 목록 | 250~350 (앨범 목록) |
| D-1 오후 | 큐레이션·실제 이용 아티스트의 앨범 트랙, 최신 발매부터 | 200~300 (앨범 트랙) |
| D | 수집 중단, 엔드포인트 호출 수와 429 기록만 감시 | 0 |

앨범 목록과 앨범 트랙은 같은 쿼터 묶음일 수 있어 같은 시간대에 섞지 않는다.

**홍보 중 예상되는 한계.** 앨범 트랙 캐시가 없는 앨범은 이용자가 열 때 Spotify를 부른다. main의 싱글 모드는 아티스트 하나에 약 40회를 부르므로, 싱글 모드가 몰리면 앨범 트랙 엔드포인트의 일일 한도가 소진될 수 있다. 소진되면 게이트가 그 엔드포인트만 막아 추가 호출은 멈추지만, 그날 캐시 없는 앨범은 곡이 비어 보인다.

**수집 스크립트.** `scripts/prelaunch-warm.ts` (targets | plan | albums | tracks). `--go` 없이는 호출하지 않는다. 호출마다 게이트를 거치고, 최근 24시간 429 기록이 있으면 시작하지 않으며, 429를 받으면 즉시 멈춘다.

## 0. 목표와 완료 기준

**목표.** 본격 홍보로 이용자가 몰리기 전에, 자주 호출될 아티스트는 이용자가 열자마자 **전곡**이 보이게 한다. 이 과정에서 Spotify 제한에는 걸리지 않는다.

**완료 기준 (아티스트 단위).** 아래 네 가지를 모두 만족하면 "준비 완료"로 본다.

| # | 기준 | 이유 |
|---|---|---|
| 1 | Spotify 아티스트 ID가 정식 매핑(url_rel/manual)되어 있다 | 검색·탐색에서 DB로 바로 뜬다 |
| 2 | 그 아티스트의 Spotify 앨범 중 **DB 트랙리스트가 없는 앨범이 5개 이하**다 | 싱글 모드는 빠진 앨범이 5개 이하일 때 전곡을 한 번에 불러온다. 초과하면 페이지 단위로 나뉜다 |
| 3 | 빠진 앨범(최대 5개)의 트랙리스트가 21일 임시 캐시에 있다 | 첫 이용자도 Spotify 호출 없이 전곡을 본다 |
| 4 | 싱글 모드 진입 테스트에서 Spotify 호출이 0회다 | 1~3의 실제 확인 |

**전체 완료 기준.** 1군(S) 아티스트 100%, 2군(A) 아티스트 90% 이상이 준비 완료.

## 2. 왜 Spotify로 미리 다 받는 방식은 안 되는가

1군 300명만 잡아도 계산이 맞지 않는다.

| 항목 | 계산 | 값 |
|---|---|---|
| 1군 전체 앨범 | 300명 × 36 | 약 10,800개 |
| DB에 없는 앨범 (현재 39% 보유) | 10,800 × 61% | 약 6,600개 |
| Spotify로 받는 데 걸리는 날짜 | 하루 100회 예산 가정 | **66일** |
| Spotify 트랙리스트 캐시 수명 | 약관상 임시 캐시 | 21일 |

받는 속도보다 캐시가 만료되는 속도가 빠르다. 그래서 전략은 두 가지로 정리된다.

1. **영구 보관할 수 있는 DB 트랙리스트(MusicBrainz, Discogs)를 최대한 늘린다.** 이게 주력이다.
2. **Spotify는 아티스트당 남는 앨범 5개 이하만 받는다.** 시점은 홍보 직전 2주 안으로 몰아서 캐시가 홍보 기간을 덮게 한다.

DB 보유율을 올렸을 때 1군의 Spotify 부담은 이렇게 바뀐다.

| DB 보유율 | 1군 빠진 앨범 | 21일마다 다시 받아야 하는 양 (하루 평균) |
|---|---|---|
| 39% (현재) | 약 6,600개 | 약 314회/일 |
| 80% | 약 2,160개 | 약 103회/일 |
| 아티스트당 5개 이하로 제한 | 최대 1,500개 | 최대 71회/일 |

## 3. 대상 아티스트 선정

### 3.1 후보 출처

| 출처 | 규모 | 비고 |
|---|---|---|
| 사용자가 준 목록 (차트, 페스티벌·J-Pop, 국내 팬덤 300, 홍대 인디 100, 아이돌 100) | 약 950명 | 이미 대부분 매핑 시도됨 |
| 야간 워밍 목록 (`scripts/warmup_artists.ts`: K-Pop, 팝, 인디, 힙합, J-Pop, 트로트) | 수백 명 | 운영에서 이미 인기 후보로 쓰는 명단 |
| 큐레이션 목록 (`curatedArtists.ts`) | 136명 | 탐색 첫 화면 노출 |
| 실제 이용 기록 (소트 결과, 앨범 목록 캐시) | 약 60명 | 가장 확실한 수요 |
| 장르 페이지·탐색 첫 화면 노출 아티스트 | 확인 필요 | 노출되면 클릭이 몰린다 |
| 홍보 시점 차트 (사용자 제공, 이름만) | 100~200명 | 홍보 2주 전에 한 번 더 |

### 3.2 등급

| 등급 | 기준 | 규모 목표 | 완료 기준 |
|---|---|---|---|
| **1군 (S)** | 실제 이용 기록 + 탐색 첫 화면 노출 + 최신 차트 + 사용자가 지정한 핵심 명단 | 약 300명 | 100% 준비 완료 |
| **2군 (A)** | 나머지 사용자 목록 + 야간 워밍 목록 | 약 1,000명 | 90% 준비 완료 |
| **3군 (B)** | 그 외 정식 매핑 아티스트 | 나머지 | 기준 1만. 이용자 요청 시 채움 |

### 3.3 저장 구조 (additive)

```
prelaunch_targets
  spotify_id    TEXT PRIMARY KEY
  name          TEXT
  tier          TEXT   -- S | A | B
  sources       TEXT[] -- chart, festival, idol100, warmup, curated, usage ...
  spotify_albums INT   -- 마지막으로 확인한 Spotify 앨범 수
  missing_albums INT   -- 그중 DB 트랙리스트 없는 수
  ready_at      TIMESTAMPTZ
  checked_at    TIMESTAMPTZ
```

`canonical_coverage` 뷰에 등급과 준비 상태를 붙인 `prelaunch_readiness` 뷰를 만들어 대시보드에서 바로 본다.

## 4. 실행 단계 (홍보 시작일 = D)

각 단계의 Spotify 호출 수를 함께 적는다. 모든 Spotify 호출은 엔드포인트 게이트(운영 반영 대기 중인 hotfix)와 일일 예산 안에서만 한다.

### 단계 0. 준비 — 지금 ~ D-35 · Spotify 0회

| 할 일 | 담당 |
|---|---|
| 엔드포인트 게이트 hotfix를 main에 병합 (호출 계수와 차단이 운영에서 동작해야 예산을 잴 수 있음) | **사용자** |
| 후보 명단을 합쳐 `prelaunch_targets`에 등급과 함께 넣기 | Claude |
| 사용자에게 1군 확정 명단 검토 요청 (추가·삭제만) | 사용자 |
| **홍보 시작일(D) 결정** | **사용자** |

### 단계 1. 아티스트 매핑 100% — D-35 ~ D-28 · Spotify 0회

- 1군·2군 중 미매핑·격리 아티스트를 MusicBrainz로 판정한다 (지금 쓰는 판정 스크립트 그대로).
- 판정이 안 되는 아티스트는 링크 요청 명단으로 사용자에게 드린다.
- MusicBrainz에 항목이 없거나 발매가 0건인 아티스트는 "DB 확보 불가"로 표시하고 단계 4의 Spotify 캐시 대상으로 넘긴다.

**완료:** 1군 매핑 100%, 2군 95% 이상.

### 단계 2. Spotify 앨범 목록 확보 + 제목 대조 — D-28 ~ D-18 · 앨범 목록 엔드포인트만 사용

- 1군부터 아티스트당 앨범 목록 1~2회 호출 (50개씩, 평균 36개라 대부분 1회).
- 받은 목록으로 **제목·발매연도·곡 수가 모두 같은** MusicBrainz 발매판과 연결한다 (상위 계획 H1). 연결 결과(Spotify 앨범 ID ↔ MB 발매판)는 영구 보관 가능한 매핑이다.
- 예산: 첫날 하루 60회로 시작. 그날 429가 없으면 이틀마다 1.5배로 올리되 하루 200회를 넘기지 않는다. 운영 트래픽 호출 수를 합쳐서 본다.
- 이 단계의 앨범 목록 캐시는 7일 뒤 만료되지만, 연결 결과는 남는다.

**예상 호출:** 1군 약 400회, 2군 약 1,300회. 하루 60~200회로 약 10일.

**사용자 도움:** 대조 결과 50건 O/X 검수 (첫 1군 50명 처리 후 한 번).

### 단계 3. 빈칸 메우기 — D-18 ~ D-14 · Spotify 0회

아티스트별 `missing_albums`가 5를 넘는 아티스트만 대상으로 한다.

| 방법 | 대상 | 담당 |
|---|---|---|
| Discogs 덤프에서 트랙리스트 추출 후 같은 규칙으로 연결 | 옛 음반, 피지컬 발매 | Claude (로컬 PC 필요) |
| 사용자 링크·MB 편집 | 매핑이 틀렸거나 MB 항목이 빈 경우 | 사용자 |
| 5개 초과가 남는 아티스트 목록 보고 | 단계 4 판단 자료 | Claude |

**완료:** 1군 전원 `missing_albums ≤ 5`. 못 맞춘 아티스트는 사유와 함께 명단으로 남긴다.

### 단계 4. 남은 앨범만 Spotify로 미리 받기 — D-14 ~ D-3 · 앨범 트랙 엔드포인트

- 1군의 빠진 앨범(아티스트당 최대 5개, 전체 최대 1,500개)을 받아 21일 캐시에 넣는다.
- 예산: 하루 100회로 시작, 단계 2와 같은 방식으로 올리되 하루 250회 상한.
- D-14에 시작하면 캐시가 D+7까지 유지된다. 홍보가 길어지면 단계 6의 갱신으로 이어간다.
- 2군은 예산이 남을 때만 한다.

**예상 호출:** 1군 최대 1,500회, 하루 100~250회로 약 7~10일.

### 단계 5. 최종 점검 — D-3 ~ D-1 · Spotify 0회

- 1군 전원에 대해 준비 완료 기준 1~3을 SQL로 확인한다.
- 1군에서 무작위 30명, 2군에서 20명을 골라 싱글 모드 진입을 자동 테스트하고, 테스트 중 엔드포인트별 호출 수 증가가 0인지 본다 (기준 4). 테스트는 이미 캐시가 채워진 뒤에만 한다.
- 결과를 사용자에게 보고한다: 준비율, 미완료 아티스트와 사유, 예상 첫 주 Spotify 호출량.

### 단계 6. 홍보 기간 유지 — D 이후

- 21일 캐시 만료 전 갱신: 1군의 Spotify 캐시 앨범을 만료 3일 전에 다시 받는다 (하루 최대 71회 수준).
- 신곡: 앨범 목록 7일 캐시와 MusicBrainz 새 발매그룹 신호로 잡는다 (상위 계획 H4).
- 이용자 요청으로 새로 뜨는 아티스트는 요청 기록 상위부터 2군으로 올려 같은 절차를 돈다.
- 매일 엔드포인트별 호출 수와 429 기록을 확인한다.

| 5 | 제목 대조 결과 50건 O/X 검수 | 단계 2 |
| 6 | 사전 수집에 Spotify 호출 예외 허용 (예산과 상한은 4장 수치) | 단계 2 시작 전 |
| 7 | 홍보 2주 전 최신 차트 명단 (이름만) | D-16 전후 |
| 8 | Discogs 덤프 처리용 로컬 PC 시간(수 시간)·디스크(약 20GB) | 단계 3 |

## 6. 확인 쿼리

```sql
-- 등급별 준비율
SELECT tier,
       count(*) AS artists,
       count(*) FILTER (WHERE ready_at IS NOT NULL) AS ready,
       round(100.0 * count(*) FILTER (WHERE ready_at IS NOT NULL) / count(*), 1) AS ready_pct
FROM prelaunch_targets GROUP BY tier ORDER BY tier;

-- 1군 중 빠진 앨범이 5개를 넘는 아티스트
SELECT name, spotify_albums, missing_albums
FROM prelaunch_targets WHERE tier = 'S' AND missing_albums > 5
ORDER BY missing_albums DESC;

-- 오늘 엔드포인트별 호출 수와 429 기록
SELECT endpoint, calls_today, blocked_until FROM spotify_endpoint_quota ORDER BY calls_today DESC;
SELECT * FROM spotify_429_log ORDER BY at DESC LIMIT 5;
```

## 7. 검토했지만 보류한 방법

**곡 1개짜리 싱글은 앨범 제목을 곡 제목으로 추정해 트랙 호출을 생략한다.**
- 앨범 중 곡 1개짜리가 34%라 효과는 크다.
- 실측(캐시 339건): 곡 제목이 앨범 제목과 완전히 같은 경우 75%, 앞부분만 같은 경우 90%.
- 10~25%는 "(feat. …)" 같은 차이로 제목이 달라지고, 곡 길이와 곡 ID도 없다. 전곡 소트에서 같은 곡이 두 번 보이거나 제목이 틀릴 수 있어 보류한다. 단계 4의 예산이 부족할 때만 사용자와 다시 논의한다.
