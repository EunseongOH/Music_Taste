> 화면을 고치거나 새로 만들기 전에 이 문서의 순서로 판단한 뒤 코드를 쓴다.

## 0. 두 가지를 동시에 만족해야 한다

1. **사용자가 생각하지 않아도 이해할 수 있어야 한다.** 화면 구조·정보 위계·레이아웃·CTA는 명확하고 예측 가능해야 한다.
2. **행동했을 때 살아 있는 경험을 느껴야 한다.** 행동에는 피드백이 있고, 필요하면 기대감·성취감·발견·안심·연결감·진행감이 설계되어야 한다.

> Structure should be predictable. Experience should feel responsive and alive.

구조까지 매번 새롭게 만들지 않는다. 반대로 구조가 일관되다는 이유로 경험을 무표정하게 만들지도 않는다.

## 1. 판단 순서

1. **User Goal** — 사용자는 무엇을 하려고 들어왔는가
2. **Flow** — 그 목적에 이르는 가장 자연스러운 경로
3. **Information Hierarchy** — 무엇을 먼저 이해해야 하는가
4. **Interaction Feedback** — 행동의 결과를 알 수 있는가
5. **Emotional Experience** — 어떤 감정이 이 경험에 도움이 되는가
6. **Visual Expression** — 그것을 어떤 시각 언어로

거꾸로 하지 않는다. 그래픽이나 모션을 먼저 만들고 UX를 끼워 맞추지 않는다.

## 2. 화면을 만들기 전에 정의할 다섯 가지

- **User Goal** — 사용자가 해결하려는 것
- **Service Goal** — 서비스가 완료되기를 바라는 행동
- **Primary Action** — 가장 중요한 행동 하나
- **Expected Emotion** — 확신·기대·재미·성취·안심·발견·소속감 중 무엇
- **Success State** — 어떤 상태가 되면 목적을 달성했다고 느끼는가

이 다섯이 불명확하면 UI부터 고치지 않는다.

## 3. 기능의 개수가 아니라 경험의 가치

기능을 더하기 전에 묻는다. 실제로 필요한가. 기존 흐름으로 안 되는가. 기능을 더하는 것보다 지금 경험을 명확하게 만드는 편이 낫지 않은가.

**More Features 보다 Better Experience.** 메뉴를 늘리는 대신 사용자가 고민하는 순간을 줄인다.

## 4. 사용자의 행동을 관찰한다

왜 들어오는가 · 무엇을 기대하는가 · 어디서 망설이는가 · 무엇을 반복하는가 · 무엇 때문에 돌아오는가 · 언제 만족하는가 · 언제 불안해지는가 · 언제 이탈하는가.

UX는 배치가 아니라 **기대 → 행동 → 결과 → 다음 행동**의 연쇄를 설계하는 일이다.

## 5~6. 첫 화면과 앱 내부 랜딩

첫 화면은 본 직후 셋을 알 수 있어야 한다: 무엇을 하는 것인가, 나에게 어떤 가치인가, 지금 무엇을 하면 되는가.

권장 구조: `Eyebrow → Headline → Supporting Description → Primary CTA → Visual`

앱 **내부**에서는 "우리가 무엇을 하는 서비스인가"보다 **"이 기능으로 무엇을 얻는가"**를 먼저 말한다. 기능명이 아니라 사용 결과를 쓴다.

- 나쁨: `음악 소트`
- 좋음: `좋아하는 곡을 하나씩 비교하며 나만의 최애곡 순위를 만들어보세요`

## 7. 상세 화면은 의사결정 순서대로

`Identity → Core Summary → Primary Action → Key Information → Supporting Information → Related Content`

대상이 무엇인지 모르는 상태에서 세부 설명부터 보여주지 않는다.

## 8. 정보 위계 — 세 단계

- **Level 1** 먼저 봐야 하는 것: 제목, 핵심 결과, 주요 콘텐츠, Primary CTA
- **Level 2** 이해를 돕는 것: 설명, 섹션 제목, 보조 수치
- **Level 3** 부가 정보: 메타데이터, 캡션, 헬퍼 텍스트

크기만이 아니라 굵기·대비·여백·위치로 위계를 만든다. 모든 요소가 중요해 보이면 아무것도 중요하지 않다.

## 9~11. 레이아웃은 예측 가능하게

섹션마다 새 디자인을 만들지 않는다. 하나의 **Section Grammar**를 정해 반복한다. 사용자는 정독하지 않고 스캔한다.

> Layout은 예측 가능하게. Content와 Response는 변화 가능하게.

예외 정보 하나 때문에 디자인 시스템을 깨지 않는다. 기존 구조 **아래에** 더한다.

## 12. 여백은 정보 구조의 일부

사용자는 정보를 덩어리 단위로 인식한다. 그룹 사이를 여백으로 나눈다. 스크롤이 길어지는 것을 지나치게 두려워하지 않는다 — 압축해서 인지 부담을 키우지 않는다.

## 13~15. 행동에는 반드시 반응이 있어야 한다

버튼을 눌렀는데 아무 일도 없는 경험을 만들지 않는다. "내가 제대로 눌렀나"를 생각하게 하지 않는다.

Pressed / Loading / Success / Toast / Progress / Inline validation / Skeleton / State transition 중 상황에 맞는 것을 준다.

좋은 인터랙션은 예쁜 것이 아니라 **불확실성을 줄인다.** 저장했으면 저장됐다고, 진행 중이면 진행 중이라고, 실패했으면 무엇이 잘못됐고 무엇을 하면 되는지 말한다.

## 14. 모션의 첫 목적은 장식이 아니다

넣기 전에 묻는다: 이 모션이 이해에 어떤 도움을 주는가.

역할: **Feedback**(처리됐음) · **Continuity**(화면 사이의 관계) · **Direction**(어디를 볼지) · **State Change**(무엇이 바뀌었는지) · **Emotional Reward**(완료·성취).

아무 역할도 없으면 제거를 검토한다.

## 16~21. 기대감·보상·진행·Social Proof

- **기대감**도 UX의 일부다. 단 예측 불가능성을 아무 데나 넣지 않는다 — 결제·설정·계정에서는 예측 가능성이 먼저다.
- **Variable Reward**를 사용 시간을 늘리려고 쓰지 않는다. 발견 자체가 목적인 곳에서만 제한적으로.
- **Progress**는 사용자가 자신의 위치를 이해하는 데 도움이 될 때만. 게임처럼 보이려고 넣지 않는다.
- **Gamification**은 서비스 목적과 연결될 때만. 의미 없는 포인트·배지를 남발하지 않는다.
- **Social Proof**는 **실제 데이터일 때만.** 가짜 숫자나 오해를 부르는 표현을 만들지 않는다.

## 22~23. 움직이게 하는 것과 조종하는 것은 다르다

쓰지 않는다: 가입은 쉽게 탈퇴는 어렵게 · 취소 버튼 숨기기 · 해지 경로 복잡하게 · 실수하도록 버튼 배치 · 거짓 희소성 · 미리 체크된 동의 · 정보 은폐 · 오해를 부르는 CTA · 죄책감을 주는 문구.

심리 원리를 쓰더라도 **사용자의 목표와 서비스의 목표가 충돌하면 사용자의 통제권을 보호한다.** 항상 묻는다 — 이 패턴이 사용자에게도 이익인가.

## 24~25. CTA와 Card

한 화면에서 Primary CTA가 여럿 경쟁하지 않게 한다. `Primary → Secondary → Tertiary Text Action`의 시각 강도를 다르게 한다.

모든 콘텐츠를 Card에 넣지 않는다. Card는 독립된 객체·반복 항목·비교 가능한 콘텐츠·별도 인터랙션·명확한 경계가 필요할 때. 단순 영역 구분이면 **Card보다 Whitespace**를 먼저 검토한다.

## 26~33. 그래픽·3D

그래픽은 단어를 그림으로 옮기는 장식이 아니라 **메시지**를 표현한다. 만들기 전에 정의한다 — 이 섹션에서 사용자가 느껴야 하는 핵심 메시지는 무엇인가.

3D는 세련돼 보인다고 쓰지 않는다. 시선 집중·추상 개념의 상징화·브랜드 감성·시각적 리듬·공간 관계에 필요할 때만. 그렇지 않으면 SVG·아이콘·일러스트·사진이 낫다.

쓴다면: 실루엣이 한눈에 읽히게(두께·베벨·곡률을 조금 과장해도 된다) · Main 하나를 정하고 Supporting을 더한다 · Foreground/Midground/Background로 공간을 만든다 · 빛의 목적은 밝게 하는 것이 아니라 **형태를 읽게 하는 것**이다(방향·대비·광원 크기).

구현은 **Static Render 기본** → Static + CSS/Framer Motion → 정말 조작이 필요할 때만 Three.js.

## 34~37. 색과 일관성

새 색을 만들기 전에 **역할**을 정의한다(Brand Primary / Background / Surface / Text Primary / Text Secondary / Border / Success / Warning / Error). "예뻐서"는 이유가 아니다.

**강조는 차이에서 생긴다.** 일반 섹션은 같은 규칙을 지키고 중요한 순간만 바꾼다.

일관성은 똑같음이 아니라 **Same Rules + Different Content**다. typography·spacing·container·radius·shadow·button size·card padding·icon size·alignment·interaction state는 일관되게. 임의의 수치를 계속 만들지 않는다.

**기존 서비스에서는 디자인 시스템을 먼저 조사한다.** 공통 컴포넌트가 이미 있으면 새로 만들지 않는다.

## 38. UX 개선과 비즈니스 로직 변경을 분리한다

디자인을 개선한다고 API·DB 스키마·상태 구조·라우팅·비즈니스 로직을 불필요하게 고치지 않는다. **UX 개선에 필요한 최소 범위만.**

## 39. 반응형

데스크톱을 축소해 모바일을 만들지 않는다. 모바일에서는 우선순위를 다시 판단한다 — 핵심 행동·상태·제목·결과를 먼저.

## 40~44. 상태 설계

**감정의 강도는 화면마다 다르다.** 온보딩·완료·결과·발견·축하·커뮤니티는 높게, 설정·결제 확인·계정·권한·오류 복구·중요한 입력은 낮게(안정성과 예측 가능성 우선).

- **Success**: 빈 화면으로 끝내지 않는다. 완료를 알리고, 성취를 느끼게 하고, 다음 행동을 제안한다. 단 강요하지 않는다.
- **Error**: "오류가 발생했습니다"로 끝내지 않는다. 무슨 일이 있었고 무엇을 할 수 있는지 말한다.
- **Empty**: "데이터가 없습니다"로 끝내지 않는다. 다음 행동을 안내한다.
- **Loading**: 아무 반응 없이 기다리게 하지 않는다. Skeleton·Spinner·Progress·Optimistic 중 맞는 것. 짧으면 과한 애니메이션을 넣지 않는다.

## 45. 접근성

세련된 UI보다 **사용 가능한 UI**가 먼저다. 대비·글자 크기·터치 영역·키보드 이동·포커스·시맨틱 HTML·alt·비활성 상태·로딩 상태·오류 상태·동작 줄이기. 미적인 이유로 접근성을 희생하지 않는다.

## 46~47. "UX 다듬어줘"를 받으면

바로 코드를 고치지 않는다. 먼저 진단한다.

**A** User Goal · **B** 어디서 막히는가 · **C** 무엇이 너무 강하거나 약한가 · **D** 피드백이 없는 행동 · **E** 너무 건조하거나 과한 곳 · **F** 디자인 시스템을 깨는 것 · **G** 지울 수 있는 것.

그다음 순서대로 고친다:
목적 → 흐름 → 정보 위계 → 레이아웃 → CTA → 피드백 → 상태 → 감정 → 타이포 → 여백 → 색 → 그래픽 → 모션 → 반응형 → 접근성 → QA.

**Visual부터 시작하지 않는다.**

## 48~55. 마무리 점검

- **3초 테스트** — 무슨 화면인지, 무엇이 중요한지, 무엇을 해야 하는지 알 수 있는가
- **Squint 테스트** — 흐릿하게 봐도 가장 중요한 것이 먼저 보이는가
- **Scan 테스트** — 읽지 않고 스크롤해도 구조가 이해되는가
- **Feedback 테스트** — "눌렀는데 무슨 일이 일어났지"가 없는가
- **Emotion 테스트** — 필요한 감정을 UI가 지원하는가, 필요 없는 곳을 꾸미고 있지 않은가
- **Consistency 테스트** — 몇 px의 불일치가 반복되지 않는가
- **Reduction 테스트** — 요소 하나를 빼도 UX가 같다면 그 요소를 다시 검토한다(배지·아이콘·카드·구분선·그림자·그라데이션·플로팅·애니메이션)
- **Ethics 테스트** — 사용자의 목적 달성을 돕는가, 지표만 올리려 행동을 조종하는가

## 피하는 것

의미 없는 그라데이션 · 모든 영역 카드 처리 · 모든 요소 그림자 · 카드 안의 카드 · 과한 글래스모피즘 · 너무 작은 제목 · 의미 없는 3D · 플로팅 오브젝트 남발 · 장식용 아이콘 남발 · 여러 Primary CTA · 좁은 여백 · 불필요한 가운데 정렬 · 모든 섹션 애니메이션 · 반응 없는 버튼 · 의미 없는 게이미피케이션 · 가짜 social proof · 강제적인 engagement · 불필요한 메뉴 · 기존 시스템을 무시한 스타일

## 평가 기준

"더 예뻐졌는가"로 평가하지 않는다.

**Understanding**(더 빨리 이해하는가) · **Direction**(다음 행동이 명확한가) · **Effort**(생각할 양이 줄었는가) · **Feedback**(결과를 즉시 아는가) · **Confidence**(상태를 확신하는가) · **Emotion**(맞는 감정인가) · **Consistency**(하나의 제품처럼 느껴지는가) · **Agency**(내 의지대로 행동한다고 느끼는가)

---

> **사용자가 화면 자체를 해석하느라 에너지를 쓰게 하지 말고,
> 사용자가 원하는 행동과 경험에 에너지를 쓸 수 있게 설계한다.**

큰 변경을 할 때는 `User Goal → 현재 문제 → 행동/심리 → UX 해결 → UI 표현 → 구현` 순서로 판단한 뒤 코드를 고친다.
